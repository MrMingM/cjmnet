# 科研问题驱动工作流（Research Workflow）

> 建立日期：2026-09-16  
> 适用项目：恶劣天气下协同感知鲁棒性研究  
> 作用：规定后续 AI 和人工研究必须遵循的统一科研流程，避免回到“先找论文拼模块 → 直接跑大实验 → 看 AP 涨没涨”的低效循环。

---

## 0. 总原则

本项目的总研究方向始终是：

> **恶劣天气下协同感知的鲁棒性。**

点云预处理、通信、融合、检测、压缩等都只是这个总问题下的子问题或技术手段，不能把某一个正在测试的模块误写成“研究方向已经改变”。

后续 AI 在提出新想法前，必须先回答：

1. 现在观察到的现象是什么？
2. 为什么会出现这个现象？
3. 有哪些互相竞争的解释？
4. 哪个最低成本实验最能区分这些解释？
5. 这个问题有没有足够大的 Oracle 上限？
6. 可部署方法是否能在 Cheap Gate 中表现出正确趋势？
7. 完整实验是否真正验证了最初声称的机制？

**禁止默认执行以下旧流程：**

> 搜一批论文 → 拼几个模块 → 训练 3–5 小时 → 看 AP → 失败后换另一个网络。

正确流程固定为：

> **现象 → 竞争假设 → 假设墓地 → 定向文献 → Oracle / Counterfactual → Cheap Gate → Full Experiment → 机制验证 → 论文叙事**

---

# 1. 现象 → 多个竞争假设

## 1.1 目标

从已经完成的实验、失败结果、case、指标异常、天气差异和模型行为中提出科学问题。

第一反应必须是：

> **“为什么会这样？”**

而不是：

> “还能加什么网络？”

## 1.2 操作要求

针对每一个值得研究的现象，至少提出若干个**真正互相竞争**的解释。

每个假设必须明确写出：

- **假设内容**：它具体声称什么；
- **为什么能解释当前现象**；
- **已有支持证据**；
- **已有反对证据**；
- **如果它是真的，还应该观察到什么**；
- **什么结果能够否定或显著削弱它**。

禁止使用无法证伪的模糊表述，例如：

- “模型能力可能不够”；
- “网络可能还需要优化”；
- “可能换一个更强 backbone 会更好”。

如果两个假设不能通过实验区分，它们不应该被当作两个独立竞争假设。

## 1.3 实验排序原则

不是平均验证所有假设，而是按照：

> **验证成本低 + 能一次排除更多解释 + 信息增益高**

排序。

优先顺序通常为：

1. 已有日志重新统计；
2. 已有 inference 输出分析；
3. case study / visualization；
4. 冻结模型 intervention；
5. 删除 / 替换 / counterfactual；
6. 小样本推理；
7. Oracle；
8. 最后才是重新训练。

## 1.4 本阶段输出

至少形成：

- 核心现象；
- 竞争假设；
- 可观察预测；
- Falsification Criteria；
- 最低成本验证实验；
- 实验优先级。

# 2. 维护“创新点墓地 / 假设墓地”

## 2.1 目标

失败实验不是简单写成：

> “A1B1 失败了。”

而要把已经付出的实验成本转化成以后不会重复支付的科研资产。

## 2.2 每一条历史路线必须记录

- **原始科学问题**；
- **原始假设**；
- **当时为什么认为它可能成立**；
- **实际使用的方法**；
- **原本预期结果**；
- **实际观察结果**；
- **失败发生在哪一层**；
- **因此真正排除了什么**；
- **没有排除什么**；
- **还留下什么问题**；
- **什么条件下值得重新启动**。

## 2.3 必须区分

### 假设失败

说明一个具体科学命题已经被实验直接反驳。

### 实现失败

说明当前 proxy、网络、loss、粒度、训练方式或干预尺度失败，但上位科学问题仍然可能成立。

二者禁止混为一谈。

例如：

> “low reliability block 删除后 AP 下降”

可以削弱：

> “低 reliability = 低 task utility”。

但不能直接推出：

> “不存在任何可预测的 task utility”。

## 2.4 AI 查重要求

未来 AI 提出任何新创新点前，都必须检查墓地：

- 核心假设是否已经做过；
- proxy 是否只是换名字；
- 输入信号是否相同；
- 干预粒度是否相同；
- loss 是否相同；
- ranking / gating 是否相同；
- 是否只是把 MLP 换成 Transformer；
- 是否已经有明确反证。

如果只是结构换名而科学假设未变化，应标记为：

> **HIGH RISK OF REPEATED IDEA**

# 3. 围绕仍然存活的假设做定向文献检索

## 3.1 目标

文献检索不再从：

> “通信模块有哪些论文？”

> “融合模块有哪些论文？”

出发。

而是围绕一个**非常具体、可以被实验回答的科学问题**检索。

例如：

- “局部 sensing quality 能否预测 collaborative perception 中的 downstream task utility？”
- “如何区分 missing evidence 与 negative evidence？”
- “有限带宽下哪些 spatial feature 真正是 detection-critical？”
- “恶劣天气下 source-specific useful evidence 为什么会在 fusion 中被抑制？”

## 3.2 AI 必须回答

针对一个仍然存活的假设，文献检索至少回答：

- 别人已经解决了什么；
- 别人的核心假设是什么；
- 使用了什么可观测信号；
- supervision / proxy 是什么；
- 使用什么方法验证；
- 哪些结论与本项目实验一致；
- 哪些结论与本项目实验冲突；
- 文献仍然没有解决什么；
- 这个空白是否恰好被本项目实验事实支持。

## 3.3 创新点来源

禁止再使用：

> 论文 A 模块 + 论文 B 模块 + 论文 C loss = 新方法

作为主要创新生成方式。

创新机会应该来自：

> **本项目已经观察到的实验事实 ∩ 文献尚未解决的空白**

即：

```text
Innovation Opportunity
=
Our Empirical Evidence
∩
Unresolved Literature Gap
```

如果只有“文献没做过”，但本项目没有证据表明这个问题真实存在，不应立即投入。

如果只有“我们观察到现象”，但已有文献已经成熟解决，也不应重复包装。

# 4. 先做 Oracle / Counterfactual 上限实验，再认真设计方法

## 4.1 目标

在设计复杂可部署方法之前，先回答：

> **即使我完美知道正确答案，这个方向最多能提升多少？**

## 4.2 Oracle 可以使用

仅在上限实验中可以使用：

- GT；
- detection loss；
- hindsight；
- clean counterpart；
- exhaustive search；
- counterfactual intervention；
- 最优 source / region / action 选择。

Oracle 不是最终方法，也不能在正式部署结果中使用。

## 4.3 示例

假设：

> “正确选择通信区域可以在 2 MiB 下基本保住 AP。”

那么先让 GT / hindsight 构造完美 selector。

若 Oracle 都明显无法保住 AP：

> **停止该方向。**

不要继续训练更大的 selector。

若 Oracle 上限明显：

再问：

> “现实推理时有哪些可部署信号可以近似这个 Oracle？”

只有这时才真正值得设计方法。

## 4.4 Oracle 必须回答两个问题

1. **问题本身有没有足够大的可恢复空间？**
2. **当前干预位置和作用尺度是否正确？**

Oracle 上限很低时，优先怀疑问题定义、候选空间或干预位置，而不是网络不够强。

---

# 5. Oracle 通过后设置 Cheap Gate

## 5.1 目标

Oracle 通过不等于应该立刻进行 3–5 小时甚至数天的完整实验。

先使用最低成本的可部署版本判断：

> **这个 Oracle 是否有可能被现实信号近似？**

## 5.2 Cheap Gate 形式

可以使用：

- 32 帧；
- 64 帧；
- 128 帧；
- 少量代表性场景；
- 少量 epoch；
- 冻结 backbone；
- 小头部；
- 线性 probe；
- 简单 ranking；
- 局部 intervention。

目的不是获得论文最终 AP，而是判断**方向是否正确**。

## 5.3 必须提前定义 Kill Criteria

实验开始前写清楚什么结果出现就停止。

例如：

- Oracle +8%，但可部署版本长期不到 +1%；
- 目标子集完全没有改善；
- FP 大量增加；
- 只在单一场景有效；
- Train 有效、validation 完全消失；
- 可部署信号 AUPRC 接近基率；
- 改善无法对应最初的科学机制。

一旦达到 Kill Criteria：

> **停止扩大实验。**

不要因为已经写了代码而继续消耗 GPU。

## 5.4 只有通过 Cheap Gate 才允许进入

- 完整 validation；
- 正式 test；
- 多 seed；
- ablation；
- cross-dataset；
- 大规模训练。

# 6. Full Experiment → 机制验证 → 论文叙事

## 6.1 Full Experiment 不只是看 AP

完整实验最终必须回答：

> **最开始提出的科学假设到底成立了吗？**

不能只回答：

> “AP +0.5。”

## 6.2 机制一致性

假设一个方法声称解决：

> “ego 没看到”和“ego 确认那里没有”被错误等价处理。

那么最终实验应该证明：

- 改善主要发生在 ego evidence 缺失的目标；
- neighbor 确实存在补充证据；
- 方法在这类 target 上的 recall / localization / score 有明确改善；
- 原本正确的 target 不应大量被破坏；
- FP 不应依靠放宽 detector threshold 暴涨获得；
- improvement 与声称的 intervention mechanism 一致。

如果整体 AP 上涨，但目标子集和机制分析不支持最初解释，则不能把 AP 提升直接写成机制成立。

## 6.3 正式实验至少应考虑

- Clean；
- Fog；
- Rain；
- Snow；
- 与冻结 baseline 公平比较；
- 正式固定 test；
- 不在 test 上调参；
- 多 seed（若涉及训练）；
- 核心 ablation；
- mechanism-specific metric；
- failure case；
- 必要时 cross-dataset / real adverse weather 验证。

## 6.4 最终论文叙事顺序

论文应该按照：

```text
真实问题
→
实验发现的失败机制
→
Oracle 证明问题值得解决
→
可部署方法近似 Oracle
→
完整实验验证
→
机制分析证明方法确实解决了声称的问题
```

而不是：

```text
模块 A
+
模块 B
+
模块 C
→
AP 提升
```

# 7. 每个研究问题的标准状态机

后续每一个新的科学问题，都建议使用以下状态：

```text
OBSERVED
  ↓
HYPOTHESES_DEFINED
  ↓
CHEAP_DIAGNOSIS
  ↓
LITERATURE_GROUNDED
  ↓
ORACLE_PASSED / ORACLE_FAILED
  ↓
CHEAP_GATE_PASSED / KILLED
  ↓
FULL_EXPERIMENT
  ↓
MECHANISM_VALIDATED / MECHANISM_NOT_VALIDATED
  ↓
PAPER_CANDIDATE / ARCHIVED
```

任何阶段失败，都应该把结论写回墓地，而不是直接删除历史记录。

# 8. AI 工作纪律

以后 AI 参与本项目时必须遵守：

1. **先读 `AI_CONTEXT.md`。**
2. **再读本文件。**
3. 若研究某个具体问题，再读取对应的 hypothesis / graveyard / experiment 文档。
4. 不得把某个子模块当前技术路线误写成整个研究方向发生改变。
5. 不得在没有 Oracle / cheap evidence 的情况下直接推荐长时间训练。
6. 不得因为一次实现失败就否定上位科学问题。
7. 不得因为代码存在就声称实验已经完成。
8. 不得把 validation / simulated weather 与正式 OPV2V-W test 混用。
9. 不得只根据 overall AP 判断机制成立。
10. 新想法必须先做墓地查重。
11. 新论文必须服务于一个已经存在的具体科学问题，而不是反过来用论文制造问题。
12. 如果已有实验足够否定一个假设，应明确停止，而不是继续“调参救方法”。

# 9. 当前项目首先应用这套流程的问题

当前优先使用本流程研究以下两个问题：

### Q-A：恶劣天气下，自车到底哪里是真的“观测不足 / 未观测”，哪里是“已经充分观察且可信为空”？

核心不是简单判断点是否可靠，而是建立区域级 observation state，并进一步判断哪些区域真正需要协同补充。

### Q-B：即使邻车拥有正确的补充证据，为什么现有融合仍然可能无法恢复目标？

重点研究 useful evidence 从“存在 → 传入 → 融合 → 检测”链路中究竟在哪一步被稀释、抑制或误用。

这两个问题后续分别按照本文第 1–6 步完整推进，禁止直接跳到网络设计。

# 10. 最终评价科研效率的方式

不要只统计：

> “本周跑了多少次实验。”

更应该统计：

> **“本周排除了多少个错误假设？”**

可以把科研效率近似理解为：

```text
Research Efficiency
≈
Information Gain
/
(GPU Hours + Human Hours)
```

一个 20 分钟的诊断实验，如果能否掉一整类错误方法，可能比一个 5 小时完整训练更有价值。
